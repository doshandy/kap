## technical-decision
title: 技术选型不是“选最新”，而是选最合适
difficulty: 基础
tags: [技术选型, 方法论]

### 题目
做技术选型时，你会从哪些维度评估一个方案？

### 答案要点
- 业务目标：解决什么问题，成功指标是什么
- 约束条件：人力、时间、现有技术栈、组织能力、部署环境
- 长期成本：学习成本、维护成本、兼容成本、迁移成本
- 风险：是否锁定供应商、是否成熟、是否有替代方案

### 延伸
- 资深工程师的价值，往往体现在“知道什么时候不引入新东西”

## upward-communication
title: 向上汇报如何做到结论先行、风险清晰
difficulty: 进阶
tags: [沟通, 汇报]

### 题目
向上级或跨部门同步技术事项时，怎样说才能让对方快速做决策？

### 答案要点
- 先说结论，再说依据和风险
- 明确“现在需要你拍板什么”
- 用业务语言解释技术影响：成本、收益、风险、时间
- 不确定的地方要标注假设，避免把猜测说成事实

### 延伸
- 管理者通常先看可决策信息，不先看技术细节

## code-review
title: 好的 Code Review 目标是提质量，不是秀水平
difficulty: 进阶
tags: [CodeReview, 协作]

### 题目
你如何定义一次高质量 Code Review？

### 答案要点
- 先关注正确性、边界条件、回归风险、可维护性，再看风格
- 评论要具体到行为和影响，而不是抽象评价
- 能给出替代方案或权衡说明，比只指出“这样不好”更有帮助
- 对新同学要兼顾教学价值，不把 review 变成压力源

### 延伸
- 好的 review 会让团队代码越来越统一，而不是越来越个人化

## incident-retro
title: 复盘与事故处理的关键不是找人背锅
difficulty: 进阶
tags: [复盘, 事故]

### 题目
线上事故发生后，技术负责人做复盘时最应该关注什么？

### 答案要点
- 还原时间线：何时发现、何时升级、何时止血、何时恢复
- 分清直接原因、根因、系统性问题
- 输出行动项：修复、监控、流程、文档、演练、责任边界
- 复盘目标是减少再次发生概率，不是简单归因给某个人

### 延伸
- 真正成熟的团队会把事故当作系统学习素材

## mentoring-growth
title: 新人带教、梯队培养与技术影响力
difficulty: 进阶
tags: [带教, 影响力]

### 题目
一个资深前端的价值，为什么不只体现在“自己写得快”？

### 答案要点
- 能建立 onboarding、模板、最佳实践，让别人更快进入有效产出
- 能把个人经验抽成文档、脚手架、组件、规范、培训材料
- 能识别团队能力断层并主动补位

### 延伸
- 技术影响力的本质是“让团队整体效率提升”，而不是个人存在感变强

## career-promotion
title: 晋升答辩与职业成长如何讲“影响力”
difficulty: 进阶
tags: [晋升, 成长]

### 题目
准备晋升材料时，怎样避免把内容写成“我做了很多事”的流水账？

### 答案要点
- 按问题、行动、结果、外溢影响来组织，而不是按时间顺序罗列事项
- 强调你如何提升系统、团队或业务的能力，而不只是完成任务
- 尽量量化：节省时间、降低故障、提升转化、减少人力成本

### 延伸
- 资深级别的叙事重点通常不是"我会很多技术"，而是"我能稳定地产生杠杆"

## ai-collaboration
title: 与 AI 工具协作的最佳实践
difficulty: 进阶
tags: [AI, 工作方式]

### 题目
作为前端，怎么和 Cursor / GitHub Copilot / ChatGPT 这些 AI 工具高效协作？

### 答案要点
- 任务分级：写样板 / 模板代码 → 高度信任 AI；架构 / 安全敏感 → 必须人审
- 上下文：给 AI 提供仓库结构、相关文件、错误信息、目标行为；越具体输出越准
- 校验：AI 写的代码必须跑过 lint / typecheck / 单测才合并，不能凭"看起来对"
- 评审视角：把 AI 当作"高产但偶尔走神的初级工程师"，关键代码要 diff 仔细看
- 安全：不要把密钥 / 用户数据 / 内部代码贴进公网 AI；用企业版或本地模型
- 学习：让 AI 解释生疏代码 / 库的设计思想，反向加速学习
- 节奏：先描述意图 → 让 AI 出方案 → 自己评估 → 再让 AI 落地实现

### 代码示例
- 提示模板（Cursor / Copilot Chat）

```
请阅读 src/composables/useFetch.ts 和 src/types/api.ts。
我需要新增一个 useMutation hook：

要求：
1. 与 useFetch 风格一致（返回 ref + computed）
2. 支持 onSuccess / onError 回调
3. 使用 TypeScript 严格类型，不要 any
4. 失败时调用全局 toast.error，参考 src/utils/toast.ts

请先列出实现方案 + 类型签名，等我确认后再写代码。
```

### 延伸
- AI 不是替代 review，而是让 review 时间花在更有价值的地方
- 团队建议建立"AI 使用规范"：哪些场景禁用、必须人工 review 的清单、敏感信息处理流程

## tech-leadership
title: 资深前端的技术 Leadership
difficulty: 资深
tags: [Leadership, 团队]

### 题目
什么时候开始体现"领导力"？没有 Manager Title 的资深工程师如何带团队？

### 答案要点
- 技术影响力：制定团队的技术决策（框架选型、性能基线、组件库），让大家信服
- 培养：1-on-1、Code Review、设计评审中给低级别同学"教练式"反馈
- 跨团队：通过文档 / 分享 / 评审标准影响其他业务线，扩大半径
- 招聘：参与面试和招聘标准制定，把好"入口质量"
- 抗风险：紧急故障 / 复杂需求时主动出来兜底，建立信任
- 推动：把好东西规范化（设计系统、监控、CI），让收益持续而不是一锤子
- 表达：写好的设计文档 / RFC，让决策可追溯、可复盘

### 代码示例
- RFC 模板骨架

```
# RFC-001: 引入 React Server Components

## 背景
- 当前 SPA 首屏 LCP 中位数 3.2s，C 端转化压力大
- 业界普遍迁向 RSC（Next 13+）

## 方案
- 选 Next.js App Router，先在「内容详情页」灰度
- 数据层用 server components 直连 DB
- 客户端组件保留交互模块

## 影响面
- 部署架构：Vercel Edge / 自建 Node
- 团队：需要 RSC 培训 + 1 周适应期
- 性能：预期 LCP -40%，bundle -25%

## 风险与回退
- 风险：第三方库不兼容 RSC
- 回退：保留 Pages Router 作为兜底分支

## 时间线
- T+0~T+1 周：POC 1 个页面
- T+2~T+4 周：产品评审 + 灰度
- T+6 周：正式发布
```

### 延伸
- 真正的领导力是"我离开后系统仍然能运转"
- 不要做"超级英雄"，要做"造英雄的工具人"

## requirement-review
title: 需求评审你怎么参与？发现需求有坑怎么处理
difficulty: 进阶
tags: [软技能, 协作, 高频]

### 一句话
进会前先看一遍 PRD 列疑点；评审时按"用户场景 → 边界 → 异常态 → 数据/性能/合规 → 排期与依赖"五线追问；不在会上 argue 实现细节；有坑写下来 + 给替代方案，不要只 say no。

### 题目
你的 PM 拉了一个评审会，需求文档你觉得有不少问题。怎么参与才显得专业且推动事情往前走？

### 答案要点
- **会前**
  - 通读 PRD 至少一遍，列疑点（不超过 10 条，按优先级排）
  - 验证假设：跟历史代码 / 数据对一下"这个功能现在是怎样的"
  - 准备技术评估：核心改动点 + 大概工时区间 + 依赖系统
- **会中提问骨架**
  - **场景**：典型用户路径走过一次（点这里 → 跳哪里 → 看到什么）
  - **边界**：极值、空状态、超长输入、并发操作、断网、权限不足
  - **异常态**：失败时显示什么、能否重试、对账怎么处理
  - **数据 / 性能 / 合规**：数据量级、QPS、隐私字段、日志埋点
  - **排期 / 依赖**：上下游什么时候 ready、要不要灰度、回滚方案
- **发现坑的姿态**
  - 不要"这做不了"，要"这样做有 X 风险，可以改成 Y"
  - 把成本量化：多 N 工时 / 多 M 个故障点 / 影响 K 用户
  - 给至少 1 个替代方案；让 PM 做权衡而不是替 PM 决策
- **结束动作**
  - 会议纪要里 owner / 截止日期写清
  - 自己产出"技术方案 1pager"作为下一步评审的输入
- **避免的坑**
  - 不在评审会上现场扣实现细节，开"技术方案会"再深聊
  - 不被 PM 一句"先做后续再说"带跑——后续往往等于"上线后用户出 bug 找你"
  - 不在公开会怼 PM；私下 1on1 反馈

### 延伸
- 反复出问题的 PM：建立"需求质量 checklist"邀请其打勾，慢慢校准
- 每个 sprint 复盘：哪些坑评审时该发现没发现，沉淀到团队 wiki

## tech-debt-governance
title: 怎么治理团队的技术债？
difficulty: 资深
tags: [软技能, 架构, 高频]

### 一句话
先量化（线上故障 / 开发效率 / 代码质量指标）→ 排优先级（影响面 × 修复成本 ROI）→ 立项（工时分配 20% 的"固定预算"）→ 持续度量。一锤子重构很难成功，要"把还债写进日常"。

### 题目
代码屎山没人愿意改，PM 永远把人堆在新需求。作为 tech lead 你怎么推动技术债治理？

### 答案要点
- **量化技术债**
  - 故障归因：每次线上 bug 标 root cause（旧设计 / 旧代码 / 缺测试 / 缺监控）
  - 开发效率：feature 交付时间趋势、新成员上手时间
  - 代码质量：sonar / eslint 错误数、复杂度高的文件 top 20、覆盖率
  - 关键指标看板（Grafana）每周晒
- **盘点 + 优先级**
  - 列"债务清单"：每条带"影响面（用户 / 团队 / 自己）× 修复成本 × 风险"
  - 用 ROI 排序：高影响 + 低成本先动
  - 别把"我不喜欢"伪装成债务
- **争取预算**
  - 用数据对管理层说话："过去半年 30% 故障来源于 X，预计投入 N 人周可降低 80%"
  - 申请固定 20%（或 1 个 sprint / 季度）"还债时间"
  - 把还债 KR 写进团队 OKR
- **执行**
  - 每个迭代挑 2-3 项，按"先加测试 → 再重构 → 再删旧代码"三段
  - 重构必须有测试兜底，不然只是换个屎山
  - 不能影响业务，灰度 + 监控
- **持续机制**
  - PR review 时逼出 TODO / FIXME 的处理
  - 上线即清死代码：feature flag 完全放量后 1 个月强制删除
  - "童子军规则"：每次改代码顺手提升 1 点（命名、抽函数、加注释）
- **失败案例**
  - "推倒重写"几乎都失败：成本爆炸 + 业务停摆 + 老 bug 全部回归
  - 推荐"绞杀者模式"（Strangler Fig）：新模块逐步替代旧模块

### 延伸
- 思考债务"换利息"：今天不还，明天加倍——把利息可视化
- 工具：sonar、husky/lint-staged、依赖更新机器人（renovate / dependabot）

## cross-team-driving
title: 跨团队推进项目你怎么搞定？
difficulty: 资深
tags: [软技能, 协作]

### 一句话
做"主 owner"心态：拉对齐会前先搞定每方关键人 1on1（避免会议上撕）；产出明确文档 + 时间表 + 依赖矩阵；每周同步进度 + 风险；要会"上升"但不滥用。

### 题目
你负责一个跨 5 个团队的大项目，进度卡在某个上游接口上。讲讲你怎么推动？

### 答案要点
- **接到项目第一周**
  - 列"涉众矩阵"：每团队 owner / 副 owner / 产出物 / deadline
  - 1on1 见每个 owner，了解他们的优先级和困难（不是发要求！）
  - 产出"项目 1pager"+ 关键路径甘特图
- **对齐会议**
  - 每周同一个时间，固定 30min；不开新闻发布会，只讨论卡点和决策
  - 会前邮件同步进度 + 风险，会上只 review 红色项
  - 决策结论写在群里 + 文档，让缺席者能追上
- **卡点处理（核心）**
  - 卡 1 天：私聊 owner 问能否帮忙
  - 卡 3 天：拉 owner + 你的双方上级在群讨论替代方案
  - 卡 1 周：升级到向上汇报；带方案不带情绪
  - 关键：每次升级前先和 owner 通气，别背刺
- **维护信任**
  - 不在会上让任何团队下不来台
  - 自己团队工作做实，给上下游留充足 buffer
  - 上游交付质量好时，公开感谢（@到他们老板）
- **写状态报告**
  - "本周完成 / 下周计划 / 阻塞 / 风险"四段
  - 红黄绿状态色一目了然，避免老板逐字看
- **避免**
  - 用 IM 一对一推进 → 没有审计 → 出问题口说无凭
  - 当传话筒 → 上下游都不爽
  - 替别人做决定 → 后面 owner 不认账

### 延伸
- RACI 矩阵明确每件事谁 R / A / C / I
- 复盘文档里写"哪里推得不好"作为团队学习

## okr-decomposition
title: 怎么把团队 OKR 拆到个人？
difficulty: 进阶
tags: [软技能, 管理]

### 一句话
公司 → 部门 → 团队 → 小组 → 个人逐层拆，每层只承接 2-3 个 KR；个人 KR 要"可量化、可独立完成、与团队关键结果直接相关"；保留 30% 个人探索空间避免压死。

### 题目
团队下季度 OKR 已经定了，怎么拆给 6 个人？

### 答案要点
- **整体节奏**
  - sprint 0（OKR 周）：1on1 沟通每个人对方向的理解
  - week 1：候选 KR 池公示，大家认领 / 调整
  - week 2：定稿，写进绩效系统
- **拆解原则**
  - 一个人 2-3 个 KR，多了等于没有
  - 每个 KR 要具体到"完成 X，使 Y 指标到 Z"，不要"提升 / 优化 / 探索"
  - 难度：60% 必达 + 40% 挑战；全是 100% 完成意味着定低了
- **平衡**
  - 业务交付 + 技术建设 + 个人成长，三类都要有
  - 不让某人只承接最难的 / 也不让某人只刷简单
  - 跨人 KR（A 完成 B 才能开始）要明示依赖
- **写法**
  - 差："优化首页性能"
  - 好："首页 LCP 从 2.8s 降至 1.5s（P75，移动端）"
- **沟通**
  - 1on1 中先听个人想法再调整
  - 解释为什么这个 KR 重要 + 对个人成长的价值
  - 给"够一够"的 KR 但配套支持（培训 / mentor）
- **跟进**
  - 每周站会快速 check
  - 月度 review 调整：偏离严重时及时补救，别等季末
  - 季末复盘：完成度 + 学到什么 + 下季度调整

### 延伸
- OKR 不和绩效奖金强绑定，否则大家会定低
- 个人探索预算（20%）做尝试性 KR，做不成不算失败
