## technical-decision

title: 技术选型不是“选最新”，而是选最合适
followups: [technical-decision-followup-1, technical-decision-followup-2, technical-decision-followup-3]
difficulty: 基础
tags: [技术选型, 方法论]

### 一句话

业务目标：解决什么问题，成功指标是什么；约束条件：人力、时间、现有技术栈、组织能力、部署环境；长期成本：学习成本、维护成本、兼容成本、迁移成本。

### 题目

做技术选型时，你会从哪些维度评估一个方案？

### 答案要点

- 业务目标：解决什么问题，成功指标是什么
- 约束条件：人力、时间、现有技术栈、组织能力、部署环境
- 长期成本：学习成本、维护成本、兼容成本、迁移成本
- 风险：是否锁定供应商、是否成熟、是否有替代方案

#### 补充说明

- 面试中不要只停留在「技术选型不是“选最新”，而是选最合适」的定义，还要解释为什么需要它、它解决了哪类问题，以及在哪些约束下会失效。
- 可以围绕 技术选型、方法论 展开：先给核心机制，再补工程场景，最后说明替代方案和取舍理由。
- 回答时要从定义、机制、边界、落地和验证五个层面展开。
- 落地时建议给出验证路径：单测覆盖边界，集成测试覆盖主链路，线上通过日志、指标或灰度观察真实效果。
- 如果答案涉及兼容性、性能或安全，要主动说明默认方案、例外场景和回滚策略。

### 追问

- 「技术选型不是“选最新”，而是选最合适」在真实项目里最容易踩到哪些边界条件？
- 你会用哪些测试、日志或指标证明这个方案有效？
- 如果需求规模、团队成本或兼容性要求变化，你会如何调整方案？

### 常见误区

- 回答「技术选型不是“选最新”，而是选最合适」时不要停在定义层，要补充适用条件、失效边界和验证方式。
- 如果没有补充输入边界、失败路径和替代方案，答案会停留在“知道概念”的层面。
- 如果不说明监控指标、发布策略和回滚方式，工程可信度会明显不足。
- 相关标签是 技术选型、方法论，回答时要补充可验证手段：如何复现问题、用什么指标判断有效、出现异常时如何降级或回滚。

### 延伸

- 资深工程师的价值，往往体现在“知道什么时候不引入新东西”

## upward-communication

title: 向上汇报如何做到结论先行、风险清晰
followups: [upward-communication-followup-1, upward-communication-followup-2, upward-communication-followup-3]
difficulty: 进阶
tags: [沟通, 汇报]

### 一句话

先说结论，再说依据和风险；明确“现在需要你拍板什么”；用业务语言解释技术影响：成本、收益、风险、时间。

### 题目

向上级或跨部门同步技术事项时，怎样说才能让对方快速做决策？

### 答案要点

- **结论先行**：第一句话给出结果或建议，再展开依据，避免让上级猜
- 明确"**现在需要你拍板什么**"：是要资源、要批准方案、还是仅同步信息
- 用**业务语言**翻译技术影响：成本（人天）、收益（指标提升）、风险（用户/营收）、时间窗口
- 不确定的地方**标注假设**（"假设 A 厂商接口 SLA 99.9%"），避免把猜测当事实
- 给出**可选项 + 推荐项**，附 trade-off 表，把选择权交回决策者

### 追问

- 「向上汇报如何做到结论先行、风险清晰」在真实项目里最容易踩到哪些边界条件？
- 你会用哪些测试、日志或指标证明这个方案有效？
- 如果需求规模、团队成本或兼容性要求变化，你会如何调整方案？

### 常见误区

- 回答「向上汇报如何做到结论先行、风险清晰」时不要停在定义层，要补充适用条件、失效边界和验证方式。
- 如果没有补充输入边界、失败路径和替代方案，答案会停留在“知道概念”的层面。
- 如果不说明监控指标、发布策略和回滚方式，工程可信度会明显不足。
- 相关标签是 沟通、汇报，回答时要补充可验证手段：如何复现问题、用什么指标判断有效、出现异常时如何降级或回滚。

### 延伸

- 管理者通常先看可决策信息，不先看技术细节

## ai-collaboration

title: 与 AI 工具协作的最佳实践
followups: [ai-collaboration-followup-1, ai-collaboration-followup-2, ai-collaboration-followup-3]
links: [11-ai-frontend/ai-prompt-engineering-front, code-review, cross-team-driving]
difficulty: 进阶
tags: [AI, 工作方式]

### 一句话

任务分级：写样板 / 模板代码 → 高度信任 AI；架构 / 安全敏感 → 必须人审；上下文：给 AI 提供仓库结构、相关文件、错误信息、目标行为；越具体输出越准；校验：AI 写的代码必须跑过 lint / typecheck / 单测才合并。

### 题目

作为前端，怎么和 Cursor / GitHub Copilot / ChatGPT 这些 AI 工具高效协作？

### 答案要点

- 任务分级：写样板 / 模板代码 → 高度信任 AI；架构 / 安全敏感 → 必须人审
- 上下文：给 AI 提供仓库结构、相关文件、错误信息、目标行为；越具体输出越准
- 校验：AI 写的代码必须跑过 lint / typecheck / 单测才合并，不能凭"看起来对"
- 评审视角：把 AI 当作"高产但偶尔走神的初级工程师"，关键代码要 diff 仔细看
- 安全：不要把密钥 / 用户数据 / 内部代码贴进公网 AI；用企业版或本地模型
- 学习：让 AI 解释生疏代码 / 库的设计思想，反向加速学习
- 节奏：先描述意图 → 让 AI 出方案 → 自己评估 → 再让 AI 落地实现

### 代码示例

- 提示模板（Cursor / Copilot Chat）

```text
请阅读 src/composables/useFetch.ts 和 src/types/api.ts。
我需要新增一个 useMutation hook：

要求：
1. 与 useFetch 风格一致（返回 ref + computed）
2. 支持 onSuccess / onError 回调
3. 使用 TypeScript 严格类型，不要 any
4. 失败时调用全局 toast.error，参考 src/utils/toast.ts

请先列出实现方案 + 类型签名，等我确认后再写代码。
```

### 追问

- 要让「与 AI 工具协作的最佳实践」上线更稳，你会如何设计效果验证、预算预警和安全兜底机制？
- 你会怎样给「与 AI 工具协作的最佳实践」建立“输出异常 -> 降级策略 -> 人工介入”闭环？
- 如果「与 AI 工具协作的最佳实践」预算受限但准确率要求较高，你会如何安排动态路由与降级阈值？

### 常见误区

- 回答「与 AI 工具协作的最佳实践」时如果只谈模型能力，不覆盖评估、成本、隐私和兜底，会缺少产品化视角。
- 只调 prompt，不建立评估集、成本预算、超时重试、内容安全和人工兜底。
- 把模型输出当确定结果使用，忽略幻觉、上下文污染、隐私泄露和可观测性。
- 相关标签是 AI、工作方式，回答时要补充可验证手段：如何复现问题、用什么指标判断有效、出现异常时如何降级或回滚。

### 延伸

- AI 不是替代 review，而是让 review 时间花在更有价值的地方
- 团队建议建立"AI 使用规范"：哪些场景禁用、必须人工 review 的清单、敏感信息处理流程

## requirement-review

title: 需求评审你怎么参与？发现需求有坑怎么处理
followups: [requirement-review-followup-1, requirement-review-followup-2, requirement-review-followup-3]

### 一句话

进会前先看一遍 PRD 列疑点；评审时按"用户场景 → 边界 → 异常态 → 数据/性能/合规 → 排期与依赖"五线追问；不在会上 argue 实现细节；有坑写下来 + 给替代方案，不要只 say no。

### 题目

你的 PM 拉了一个评审会，需求文档你觉得有不少问题。怎么参与才显得专业且推动事情往前走？

### 答案要点

- **会前**
  - 通读 PRD 至少一遍，列疑点（不超过 10 条，按优先级排）
  - 验证假设：跟历史代码 / 数据对一下"这个功能现在是怎样的"
  - 准备技术评估：核心改动点 + 大概工时区间 + 依赖系统
- **会中提问骨架**
  - **场景**：典型用户路径走过一次（点这里 → 跳哪里 → 看到什么）
  - **边界**：极值、空状态、超长输入、并发操作、断网、权限不足
  - **异常态**：失败时显示什么、能否重试、对账怎么处理
  - **数据 / 性能 / 合规**：数据量级、QPS、隐私字段、日志埋点
  - **排期 / 依赖**：上下游什么时候 ready、要不要灰度、回滚方案
- **发现坑的姿态**
  - 不要"这做不了"，要"这样做有 X 风险，可以改成 Y"
  - 把成本量化：多 N 工时 / 多 M 个故障点 / 影响 K 用户
  - 给至少 1 个替代方案；让 PM 做权衡而不是替 PM 决策
- **结束动作**
  - 会议纪要里 owner / 截止日期写清
  - 自己产出"技术方案 1pager"作为下一步评审的输入
- **避免的坑**
  - 不在评审会上现场扣实现细节，开"技术方案会"再深聊
  - 不被 PM 一句"先做后续再说"带跑——后续往往等于"上线后用户出 bug 找你"
  - 不在公开会怼 PM；私下 1on1 反馈

## tech-debt-governance

title: 怎么治理团队的技术债？
followups: [tech-debt-governance-followup-1, tech-debt-governance-followup-2, tech-debt-governance-followup-3]
difficulty: 资深
tags: [软技能, 架构, 高频]

### 一句话

先量化（线上故障 / 开发效率 / 代码质量指标）→ 排优先级（影响面 × 修复成本 ROI）→ 立项（工时分配 20% 的"固定预算"）→ 持续度量。一锤子重构很难成功，要"把还债写进日常"。

### 题目

代码屎山没人愿意改，PM 永远把人堆在新需求。作为 tech lead 你怎么推动技术债治理？

### 答案要点

- **量化技术债**
  - 故障归因：每次线上 bug 标 root cause（旧设计 / 旧代码 / 缺测试 / 缺监控）
  - 开发效率：feature 交付时间趋势、新成员上手时间
  - 代码质量：sonar / eslint 错误数、复杂度高的文件 top 20、覆盖率
  - 关键指标看板（Grafana）每周晒
- **盘点 + 优先级**
  - 列"债务清单"：每条带"影响面（用户 / 团队 / 自己）× 修复成本 × 风险"
  - 用 ROI 排序：高影响 + 低成本先动
  - 别把"我不喜欢"伪装成债务
- **争取预算**
  - 用数据对管理层说话："过去半年 30% 故障来源于 X，预计投入 N 人周可降低 80%"
  - 申请固定 20%（或 1 个 sprint / 季度）"还债时间"
  - 把还债 KR 写进团队 OKR
- **执行**
  - 每个迭代挑 2-3 项，按"先加测试 → 再重构 → 再删旧代码"三段
  - 重构必须有测试兜底，不然只是换个屎山
  - 不能影响业务，灰度 + 监控
- **持续机制**
  - PR review 时逼出 TODO / FIXME 的处理
  - 上线即清死代码：feature flag 完全放量后 1 个月强制删除
  - "童子军规则"：每次改代码顺手提升 1 点（命名、抽函数、加注释）
- **失败案例**
  - "推倒重写"几乎都失败：成本爆炸 + 业务停摆 + 老 bug 全部回归
  - 推荐"绞杀者模式"（Strangler Fig）：新模块逐步替代旧模块

### 追问

- 推动「怎么治理团队的技术债」落地时，你会如何设计灰度、回滚和迁移路径？
- 如果团队成员能力和历史包袱不一致，你会如何拆阶段推进？
- 你会用哪些指标判断这个工程方案长期值得维护？

### 常见误区

- 回答「怎么治理团队的技术债？」时如果只给目标架构，不讲迁移、灰度和回滚，方案很难真正落地。
- 只给方案图，不说明约束、迁移路径、灰度策略、回滚和长期维护成本。
- 忽略团队协作和历史包袱，导致设计在文档里成立，在真实项目里落不下去。
- 相关标签是 软技能、架构、高频，回答时要补充可验证手段：如何复现问题、用什么指标判断有效、出现异常时如何降级或回滚。

### 延伸

- 思考债务"换利息"：今天不还，明天加倍——把利息可视化
- 工具：sonar、husky/lint-staged、依赖更新机器人（renovate / dependabot）

title: 跨团队推进项目你怎么搞定？

### 题目

你负责一个跨 5 个团队的大项目，进度卡在某个上游接口上。讲讲你怎么推动？

### 答案要点

- **接到项目第一周**
  - 列"涉众矩阵"：每团队 owner / 副 owner / 产出物 / deadline
  - 1on1 见每个 owner，了解他们的优先级和困难（不是发要求！）

  - 卡 1 天：私聊 owner 问能否帮忙
  - 卡 3 天：拉 owner + 你的双方上级在群讨论替代方案

  - 不在会上让任何团队下不来台
  - 自己团队工作做实，给上下游留充足 buffer
  - 上游交付质量好时，公开感谢（@到他们老板）
- **写状态报告**
  - "本周完成 / 下周计划 / 阻塞 / 风险"四段
  - 红黄绿状态色一目了然，避免老板逐字看
- **避免**
  - 用 IM 一对一推进 → 没有审计 → 出问题口说无凭
  - 当传话筒 → 上下游都不爽
  - 替别人做决定 → 后面 owner 不认账

## okr-decomposition

title: 怎么把团队 OKR 拆到个人？
followups: [okr-decomposition-followup-1, okr-decomposition-followup-2, okr-decomposition-followup-3]
difficulty: 进阶
tags: [软技能, 管理]

### 一句话

公司 → 部门 → 团队 → 小组 → 个人逐层拆，每层只承接 2-3 个 KR；个人 KR 要"可量化、可独立完成、与团队关键结果直接相关"；保留 30% 个人探索空间避免压死。

### 题目

团队下季度 OKR 已经定了，怎么拆给 6 个人？

### 答案要点

- **整体节奏**
  - sprint 0（OKR 周）：1on1 沟通每个人对方向的理解
  - week 1：候选 KR 池公示，大家认领 / 调整
  - week 2：定稿，写进绩效系统
- **拆解原则**
  - 一个人 2-3 个 KR，多了等于没有
  - 每个 KR 要具体到"完成 X，使 Y 指标到 Z"，不要"提升 / 优化 / 探索"
  - 难度：60% 必达 + 40% 挑战；全是 100% 完成意味着定低了
- **平衡**
  - 业务交付 + 技术建设 + 个人成长，三类都要有
  - 不让某人只承接最难的 / 也不让某人只刷简单
  - 跨人 KR（A 完成 B 才能开始）要明示依赖
- **写法**
  - 差："优化首页性能"
  - 好："首页 LCP 从 2.8s 降至 1.5s（P75，移动端）"
- **沟通**
  - 1on1 中先听个人想法再调整
  - 解释为什么这个 KR 重要 + 对个人成长的价值
  - 给"够一够"的 KR 但配套支持（培训 / mentor）
- **跟进**
  - 每周站会快速 check
  - 月度 review 调整：偏离严重时及时补救，别等季末
  - 季末复盘：完成度 + 学到什么 + 下季度调整

## interview-self-introduction-basic

title: 资深前端的自我介绍怎么讲不像背简历？
followups: [interview-self-introduction-basic-followup-1, interview-self-introduction-basic-followup-2, interview-self-introduction-basic-followup-3]
difficulty: 基础
tags: [面试, 自我介绍, 基础]

### 一句话

一句定位 + 一段重点项目 + 一句技术爱好；时间控制在 60-90 秒，主动给面试官"想追问"的钩子。

### 题目

请准备一段 60-90 秒、能让面试官有兴趣追问的自我介绍。

### 答案要点

- **结构**：身份 → 近期项目 → 个人偏好 / 学习
- **金句开头**：「我是 X，过去 N 年主要做 Y，最近一段在做 Z」一句话讲清定位
- **重点项目用数字 + 抽象**：例如"把 SSR 首屏从 4.5s 压到 1.6s"，"把构建从 3min 拆成 35s"
- **留钩子**：刻意提一两个有故事的关键词（DAG 编辑器 / Worker 线程池 / 自研监控 SDK），面试官多半会顺势追问
- **避雷**：别背简历、别说"我是个 hardworking 的人"、别讲个人生活（除非问到）

### 代码示例

```text
我是 csh，前端工程师，过去 8 年大部分时间在数据可视化方向，最近一年在做一个基于
DAG 的数据调度平台的核心交互——SQL 工作台 + Schedule Editor。

最有代表性的两个改动：把 Monaco 多 Tab 状态做了 IndexedDB 持久化，掉电也能续作；
和把首屏 chunk 从 1.4MB 砍到 480KB（routePreload + 第三方拆分）。

平时关注 RSC / WebGPU 这些新方向，业余时间在做一个面试自查站。
```

### 常见误区

- 1 分钟讲 5 个项目 → 没重点
- 全是 "我做了 X" 没数字 → 听不出影响面
- 讲到一半被打断不会接 → 提前练 30s / 60s / 120s 三个版本

### 追问

- 怎么讲那些"做了但没结果"的项目
- 如何处理"为什么离职"
- 跨级面试（面 P7 但岗位是 P8）怎么调整介绍

### 延伸

- 大厂面试官常用 STAR 框架追问：Situation / Task / Action / Result
- 把自我介绍录音回放是最好的练习方式

## ttm-decision-tradeoff

title: Time to Market 决策：完美方案晚三个月 vs 可用方案明天上线
difficulty: 资深
tags: [决策, 交付, 业务思维]
followups: [ttm-decision-tradeoff-followup-1, ttm-decision-tradeoff-followup-2, ttm-decision-tradeoff-followup-3]

### 一句话

Time to Market 决策不是“选快或选好”，而是先识别窗口期与事故成本，再做可逆性判断：能快速上线且可回补的先上，难回滚且高风险的先守底线。

### 题目

你负责一个关键需求：完整方案要 3 个月，可用方案 2 周能上线。作为资深前端你会怎么做决策，怎么跟产品、业务和管理层讲清楚“为什么现在这样选”？

### 答案要点

- 先把决策问题从“技术好坏”改成“业务窗口 + 风险暴露”：窗口期错过的损失、线上事故代价、后续迭代可行性要一起算，不能只比实现优雅度。
- 做可逆性分层：可快速回滚、可灰度、可补齐的能力优先走快路径；涉及安全、资金、核心数据一致性的部分必须先守住底线，再谈提速。
- 给出双轨方案而不是单选题：短期上线最小可用版本（MVP），同时明确技术债清单、回补里程碑、触发升级条件，避免“先上线”变成“永远不补”。
- 沟通时用业务语言：说明本次选择对收入、转化、留存、投诉率、团队产能的影响，并且同步给出失败阈值和回滚动作，让管理层可以拍板。
- 复盘看结果而不是看立场：上线后对比目标指标和风险指标，若收益不达标或隐患持续累积，要主动切换回“补基础能力优先”的节奏。

### 常见误区

- 把 Time to Market 简化成“快就是对”，忽略安全、合规和数据一致性，导致短期上线换来长期返工。
- 只讲技术取舍，不讲业务收益和失败边界，管理层无法基于你的信息做决策。
- 先上线但没有技术债回补计划和责任人，最后演变成系统性长期负担。

### 追问

- 如果业务方要求“绝不延期”，但你判断当前方案事故概率高，你会如何沟通并推动重排优先级？
- 当上线后指标短期改善、但维护成本持续上升时，你会怎么判断是否需要二次重构？
- 你会用哪些里程碑和阈值，确保“快交付”不会演变成“无限透支未来”？

### 延伸

- 资深工程师的价值不是永远坚持最完美方案，而是在不确定约束下给出“可执行且可回退”的判断。
- 可以把 Time to Market 决策模板化：业务目标、约束、候选方案、风险、回滚、回补计划、验收指标。

### 一句话

前端方案要拿到资源，必须把“技术收益”翻译成“业务收益 - 总成本”：指标提升是否真实、能否持续、要花多少钱、多久回本，这些都要能量化说明。

### 题目

当你推动一项前端优化（例如性能、体验、稳定性）需要跨团队投入时，如何用 ROI 视角说服业务和管理层支持？

### 答案要点

- 先定义业务目标和主指标：是提升转化、降低流失、减少客服成本，还是提升复购；没有明确目标，任何技术收益都很容易被质疑“和业务无关”。
- 指标拆解要覆盖漏斗链路：曝光 -> 点击 -> 下单 -> 支付或注册 -> 激活 -> 留存；并明确你影响的是哪一段、预期提升幅度、统计口径和观察周期。
- 成本核算不能只算研发人天：还要包含联调成本、测试回归、发布风险、监控成本、后续维护成本，避免“上线看起来赚了，长期反而亏”。
- 给出保守/中性/乐观三档收益估算，并明确触发止损条件；这样即使结果不及预期，也能快速调整而不是继续沉没成本。
- 上线后要做因果复核：通过 A/B、分流或对照时间窗验证收益是否来自这次改动，避免把自然波动或大盘变化误当成项目成果。

### 常见误区

- 只拿 Lighthouse 分数或技术指标当成果，不去映射业务漏斗，业务方很难认可投入价值。
- ROI 只算收益不算维护成本，导致方案在评审时通过、在长期运营中失血。
- 不设止损线和复盘节奏，投入后即使效果不佳也无法及时调整策略。

### 追问

## stakeholder-decision-memo

### 一句话

很多协作低效不是“技术方案不好”，而是“决策信息不完整”：一份可执行的 Decision Memo 要把问题边界、候选方案、取舍逻辑、风险回退和行动责任写到可直接决策的粒度。

### 题目

你会如何写一份跨团队都能读懂、且能在评审会上快速拍板的技术决策备忘录？

### 答案要点

- 先定义决策问题：当前要解决什么、什么不在本次范围内，防止会中跑题。
- 候选方案至少两种，并写清“为什么不选”的关键理由，避免只展示单一路径。
- 取舍必须量化：交付周期、人力成本、风险暴露窗口、可维护性和业务影响要有对比口径。
- 写明执行条件：负责人、里程碑、依赖方、验收指标、失败触发条件和回滚方案。
- 会前异步预评审、会中聚焦未决项、会后发布单一结论文档，减少反复沟通损耗。
- 对高不确定项单列“验证实验”，先小规模试点再决策全量推进。

### 代码示例

```markdown
# Decision Memo: 订单页渲染链路改造

## Decision

- 是否将订单详情页从 CSR 迁到 SSR + 缓存分层

## Options

1. 维持 CSR（开发快，首屏慢）
2. SSR + 缓存（首屏快，运维复杂度上升）

## Trade-offs

- 交付：2 周 vs 4 周
- 预估收益：LCP P75 下降 900ms
- 风险：缓存一致性、回滚复杂度

## Rollback

- 保留旧渲染路径开关 2 个版本周期
- 关键指标劣化超过阈值 10 分钟内切回
```

- 「决策备忘录（Decision Memo）怎么写，才能让跨角色快速拍板」在真实项目里最容易踩到哪些边界条件？
- 你会用哪些测试、日志或指标证明这个方案有效？
- 如果需求规模、团队成本或兼容性要求变化，你会如何调整方案？

### 常见误区

- 备忘录只写方案，不写范围边界和失败预案，导致会上无法决策。
- 只讲技术语言，不翻译为业务影响，关键干系人无法判断优先级。
- 会后没有行动项与责任追踪，决策结论无法落地。

### 延伸

- 建议为团队建立统一决策模板，降低跨项目沟通成本。
- 重大决策可设置复审时间，避免结论长期过期仍被机械沿用。

## conflict-negotiation-playbook

### 一句话

跨团队冲突常见失败点不在技术细节，而在“目标口径不一致”：先统一目标和约束，再把分歧拆成可验证项，才能从情绪争论转成可执行协商。

### 题目

当产品、研发、测试、运营对同一方案意见冲突且都很坚持时，你会如何推动达成共识并确保后续执行？

### 答案要点

- 先从“立场”回到“目标”：明确共同目标、不可妥协约束、可协商变量。
- 把冲突拆成事实分歧与偏好分歧：事实分歧靠数据验证，偏好分歧靠风险与收益协商。
- 采用“最小一致方案”：先达成可落地最小版本，再约定后续增量演进路径。
- 对关键争议点做短周期实验（1-2 周）获取证据，减少口水战。
- 会议机制要收敛：会前同步材料、会中只决策、会后发布行动项与截止时间。
- 对未达成一致的风险显式登记并设置监控阈值，避免问题上线后“无人负责”。

### 代码示例

```ts
type ConflictItem = {
  topic: string;
  impact: number; // 1-5
  urgency: number; // 1-5
  confidence: number; // 1-5，证据充分程度
};

// 优先处理“高影响 + 高紧急 + 低证据”的争议
function negotiationPriority(x: ConflictItem) {
  return x.impact * 0.4 + x.urgency * 0.4 + (6 - x.confidence) * 0.2;
}
```

### 常见误区

- 只追求“谁赢谁输”，忽略共同目标和长期协作关系。
- 会议上临时拍板，但不沉淀决策依据，后续容易反复争论。
- 冲突解决后没有验证与复盘，导致同类问题重复出现。

## high-pressure-decision-communication-matrix

### 一句话

高压场景下最怕“大家都在沟通，但没人负责决策”：把拍板权、同步路径和兜底动作做成沟通矩阵，才能在压力下保持节奏和秩序。

### 题目

线上出现重大异常，需要在 30 分钟内决定“降级、回滚还是继续观察”。你会如何组织跨团队沟通，让决策快速且可追溯？

### 答案要点

- 先定义决策角色：Decision Owner、技术 Owner、业务 Owner、沟通 Owner 各自职责清晰。
- 把信息分层：核心结论（1 句话）-> 证据（3 条）-> 风险与备选（2 套）避免信息淹没。
- 升级路径要明确：什么阈值触发升级、升级给谁、谁最终拍板要提前约定。
- 沟通节奏要固定：5-10 分钟一个状态更新，减少“各群分散同步”造成的信息漂移。
- 决策后立刻落地动作清单：谁执行、截止时间、回看指标、失败兜底必须写明。
- 事故后复盘沟通效率：决策耗时、误传次数、重复讨论点沉淀为下一次模板。

  if (input.errorRate > 0.03 || input.businessDrop > 0.05) return 'rollback';
  if (input.recoveryETAmin > 20) return 'degrade';
  return 'observe';
}

### 题目

如果面试官追问：预算收紧、交付窗口变短时，你会怎样调整这套僵局止损方案，既不拖项目也不牺牲质量？

### 答案要点

#### 核心回答

- 先做优先级收缩：只处理“高影响、高不可逆”的争议，低影响议题延后或并行异步。
- 时间盒从天级改为小时级，超时自动进入拍板，避免因预算紧导致讨论无限拉长。
- 证据门槛做分层：关键决策要硬证据，次级决策允许“快速试点 + 复盘纠偏”。

#### 学习抓手

- 回答时给一个“你主动砍掉低优先项”的例子，体现真实取舍能力。
- 讲清“快”与“稳”如何平衡：哪些环节能省，哪些环节绝不能省。
- 结尾说明回补动作：窗口过去后如何补齐文档、复盘和知识沉淀。
