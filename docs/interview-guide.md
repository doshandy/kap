# 面试技巧与常见问题手册

这份手册不属于专业题库，不进入学习计划、复习、抽题和临考模式。它更像面试前后的“软技能备忘录”：帮助你把技术能力表达出来，也帮助你判断机会是否值得继续推进。

## 面试前：把准备从“刷题”变成“可交付材料”

### 1. 准备一份 90 秒自我介绍

自我介绍不要复述简历流水账，建议固定成四段：

- 我是谁：年限、主要技术栈、最近的业务类型。
- 我解决过什么问题：挑 1-2 个代表性项目，强调复杂度和结果。
- 我为什么匹配这个岗位：结合 JD 里的关键词，比如性能、工程化、跨端、AI、数据可视化。
- 我希望进一步聊什么：主动抛出你最有把握的项目或专题。

示例结构：

> 我主要做前端工程和复杂业务系统，最近几年更多在 Vue/React、工程化、性能优化和可观测性方向。上一段项目里，我负责过从首屏性能、错误监控到组件库治理的一整套改造，核心结果是把关键页面 LCP 和错误定位效率做到了可量化提升。这个岗位提到需要工程化和复杂场景落地，我比较匹配，也可以重点展开我做过的性能治理和前端质量体系。

### 2. 准备 3 个“主项目故事”

每个主项目都建议按 `背景 -> 目标 -> 方案 -> 难点 -> 结果 -> 复盘` 准备。不要只讲“我用了什么技术”，要讲“为什么这么做，以及怎么证明有效”。

- 背景：业务为什么需要这个项目？当时有什么约束？
- 目标：指标是什么？性能、稳定性、效率、收入、转化还是成本？
- 方案：你如何拆解问题？为什么不用别的方案？
- 难点：最难的是技术、组织协同、历史包袱还是线上风险？
- 结果：最好有数据；没有数据也要有可验证事实。
- 复盘：如果重做一次，你会怎么改？

### 3. 准备“证据”

面试官很容易区分“做过”和“听过”。准备证据可以显著提高可信度：

- 性能类：LCP、INP、CLS、JS 体积、接口耗时、错误率。
- 工程化类：构建耗时、发布频次、回滚时间、CI 成功率、测试覆盖。
- 稳定性类：报警数量、MTTR、重复故障下降、错误归因效率。
- 业务类：转化率、留存、客服工单减少、人工操作减少。
- 协作类：文档、规范、迁移计划、灰度方案、培训材料。

## 项目表达：用 STAR，但不要机械套模板

STAR 是 `Situation / Task / Action / Result`，但真实面试里更好用的是下面这个顺序：

1. 一句话结论：这个项目解决了什么问题。
2. 背景约束：为什么难，难在哪里。
3. 你的角色：你负责决策、实现、推进还是兜底。
4. 技术方案：关键设计和取舍。
5. 风险控制：灰度、回滚、监控、兼容。
6. 结果复盘：数据、影响、遗留问题。

如果讲复杂项目，建议每 2-3 分钟停一下：

> 这里我先讲整体方案，如果你希望，我可以继续展开里面的性能治理、组件拆分或发布灰度细节。

这能让面试更像对话，而不是背稿。

## 技术题回答：先结论，再边界

很多候选人答技术题会输在“知道很多，但没有结构”。推荐固定成五层：

1. 定义/结论：先回答是什么。
2. 核心机制：解释为什么。
3. 场景：什么时候用。
4. 边界和坑：什么时候不用，哪里会失败。
5. 工程落地：如何测试、监控、灰度和回滚。

例如被问“为什么 Vite dev 更快”：

- 结论：Vite dev 主要快在开发阶段利用浏览器原生 ESM，避免启动时全量 bundle。
- 机制：源码按需转换，依赖预构建用 esbuild，HMR 更新粒度更小。
- 场景：中大型项目启动和热更新收益明显。
- 边界：生产仍要 bundle；插件兼容、monorepo、预构建缓存可能带来问题。
- 落地：看冷启动、热更新耗时、依赖预构建命中率和团队插件生态。

## 不会的问题怎么答

不会并不可怕，最差的是装懂。建议使用“三步法”：

1. 先承认边界：这个细节我没有在线上深入踩过。
2. 说可推导部分：但从机制上我会先这样判断。
3. 给验证路径：如果在项目里遇到，我会怎么查文档、写 demo、看源码或做实验。

示例：

> 这个 API 的具体参数我不能保证完全准确，但我知道它主要解决的是 X 问题。我的判断是它会影响 Y，因为底层机制是 Z。如果实际落地，我会先用最小 demo 验证 A/B 两种情况，再补兼容性和异常路径测试。

这样比直接说“不会”更体现工程思维，也比硬编答案更可靠。

## 被追问时如何稳住

追问通常不是刁难，而是在确认你是否真的做过、是否能处理边界。常见追问类型：

- 为什么不用另一个方案？
- 线上出问题怎么回滚？
- 数据指标怎么证明有效？
- 如果流量扩大十倍怎么办？
- 如果低端机/弱网/旧浏览器怎么办？
- 如果团队里其他人维护不了怎么办？

回答时不要只加细节，要先识别追问方向：

- 方案对比：讲约束、代价、团队熟悉度、生态和长期维护。
- 稳定性：讲灰度、监控、报警、降级和回滚。
- 性能：讲瓶颈定位、指标、采样和用户体感。
- 协作：讲规范、文档、自动化、评审机制。

## 常见 HR 问题

### 1. 为什么离职 / 为什么看机会？

不要攻击前公司、前领导或同事。更稳妥的表达是：

- 当前阶段成长空间有限，希望承担更复杂的技术或业务问题。
- 希望进入更匹配自己方向的团队，比如工程化、性能、AI、复杂前端平台。
- 希望业务规模、技术深度或团队协作方式更适合长期发展。

示例：

> 我在当前团队完成了几个主要阶段的建设，后续更多是维护和小迭代。我希望下一阶段能参与更复杂的工程体系建设，尤其是性能、质量和前端平台化方向，所以开始看更匹配的机会。

### 2. 你的优点是什么？

不要说“学习能力强”这种空话，最好绑定证据：

- 能把复杂问题拆成可落地任务。
- 对线上质量和可观测性敏感。
- 能推动跨团队协作。
- 能从业务目标倒推技术方案。

示例：

> 我的优势是工程闭环意识比较强，不只把功能写完，还会关注上线风险、监控指标和后续维护。比如之前做性能治理时，我不是只改代码，而是把指标采集、灰度发布、告警和复盘文档一起补齐。

### 3. 你的缺点是什么？

不要说致命缺点，也不要把优点伪装成缺点。建议说“已经意识到，并有改进方式”的缺点：

- 过去容易过早进入细节，现在会先对齐目标和边界。
- 过去对文档投入不足，现在会把关键决策沉淀为 ADR 或设计文档。
- 过去倾向自己解决问题，现在会更早同步风险和寻求协作。

### 4. 为什么选择我们？

不要只说“贵司平台大”。建议从三层回答：

- 业务：你理解这个业务解决什么问题。
- 技术：岗位里的技术挑战和你的经验匹配。
- 成长：这个机会能让你在哪些方向继续成长。

## 反问面试官

反问不是客套，它能帮助你判断岗位质量。可以准备这些问题：

- 这个岗位入职 3-6 个月最希望解决什么问题？
- 团队当前最大的前端技术挑战是什么？
- 前端在需求评审、技术方案和排期里有多大决策空间？
- 团队如何衡量质量？有错误率、性能、测试或稳定性指标吗？
- 线上事故如何复盘？是否有灰度、回滚和监控体系？
- 这个岗位的成长路径是什么？偏业务专家、技术专家还是团队管理？
- 如果我加入，最可能和哪些角色协作？产品、后端、设计、测试、数据分别如何配合？

尽量避免只问薪资、加班、福利。不是不能问，而是建议放在 HR 阶段。

## 薪资沟通

薪资问题的核心是“不要过早暴露底线”。建议：

- 先了解岗位级别、职责范围和整体包结构。
- 如果必须给期望，给区间而不是单点。
- 说明你关注总包、成长空间、团队匹配，不只看月薪。
- 不要编造 offer，但可以说“我会结合市场和岗位职责综合评估”。

示例：

> 我会结合岗位职责、级别和整体包来看。如果按我目前经验和市场情况，希望总包大概在 X 到 Y 区间。当然我也会看团队匹配度和成长空间。

## 远程 / 现场 / 电话面试注意事项

### 远程面试

- 提前测试摄像头、麦克风、网络和屏幕共享。
- 桌面不要打开无关窗口，避免泄露信息。
- 代码题准备一个熟悉的编辑器环境。
- 回答时比线下更需要结构化，因为远程更容易被打断。

### 现场面试

- 带好身份证、简历、纸笔。
- 不要迟到；如果不可避免，提前说明。
- 白板题先确认输入输出和边界，再写解法。
- 不确定时可以边说边推导，不要长时间沉默。

### 电话面试

- 找安静环境，语速放慢。
- 回答更要分点，因为没有表情和白板辅助。
- 对方听不清时及时确认，不要硬讲。

## 面试后复盘

每场面试结束后，建议立刻记录：

- 被问到了哪些技术点？
- 哪些问题答得不顺？
- 哪些项目细节被追问？
- 是否暴露了表达、边界、数据或方案对比不足？
- 对方团队的工作方式和岗位预期是什么？
- 下一场要补哪 3 个点？

复盘时不要只写“某题不会”，要写“为什么不会”：

- 概念不清：需要回到基础原理。
- 代码不会写：需要补最小实现。
- 边界遗漏：需要补异常、兼容、性能、安全。
- 表达不顺：需要重写一版 2 分钟回答。
- 项目证据不足：需要补指标和事实。

## Offer 选择

如果同时有多个机会，不建议只看薪资。可以按这些维度打分：

- 业务是否健康：增长、盈利、战略重要性。
- 团队是否靠谱：直接 leader、协作方式、技术氛围。
- 岗位是否有空间：是否只是填坑，还是能解决核心问题。
- 技术是否成长：复杂度、工程成熟度、学习曲线。
- 风险是否可接受：试用期、加班强度、组织变化、地点。
- 回报是否匹配：现金、年终、股票、福利、涨薪机制。

一个简单判断：

> 如果薪资高但你预感会持续消耗，要谨慎；如果薪资略低但团队强、空间大、方向对，也值得认真评估。

## 红旗信号

遇到这些情况要谨慎：

- 面试过程一直贬低前任或候选人。
- 岗位职责含糊，但要求“来了什么都做”。
- 对线上质量、排期和技术债完全没有机制。
- 频繁强调抗压，但说不清楚为什么压力大。
- 对薪资、级别、试用期规则说法前后不一致。
- 面试官不愿回答团队现状和岗位目标。
- 过度依赖个人英雄主义，没有评审、文档、测试和监控。

## 绿旗信号

这些通常是好信号：

- 面试官能清楚说明岗位目标和当前问题。
- 技术追问关注权衡、边界和落地，而不是背诵。
- 团队有代码评审、灰度、监控、复盘机制。
- 对新人前 3 个月有明确预期。
- 能坦诚说明团队问题，也能说明正在如何改。
- 尊重候选人的提问，沟通清晰。

## 最后检查清单

面试前一天可以按这个清单过一遍：

- 自我介绍是否能控制在 90 秒内？
- 三个主项目是否能各讲 3-5 分钟？
- 每个项目是否有数据、难点、取舍和复盘？
- 高频技术题是否能按“结论 -> 原理 -> 边界 -> 落地”回答？
- 是否准备了不会问题的表达方式？
- 是否准备了反问面试官的问题？
- 简历里的每个技术词是否都能解释？
- 是否知道目标公司的业务、岗位和技术关键词？
- 是否准备了面试后复盘模板？

真正稳定的面试表现，不是把所有题背完，而是能把自己做过的事情讲清楚，把不会的边界讲诚实，把方案的取舍讲可靠。
